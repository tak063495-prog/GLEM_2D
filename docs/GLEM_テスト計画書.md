## 1. 目的・範囲

### 1.1 目的

本計画は、GLEM の実装品質を保証するためのテスト活動の計画を定める。対象は機能仕様書の受入基準 A-1〜A-6 と詳細設計書 §8.2 で定義されたテスト項目 T-01〜T-12 である。

### 1.2 テスト対象と非対象

| 区分 | 内容 |
|---|---|
| 対象 | `GLEM.Core`（モデル・バリデータ・解析エンジン・IO）、`GLEM.App`（画面操作フロー）、`.glem` ファイル形式の互換性、性能 |
| 非対象 | OS/ドライバレベルの互換性テスト、負荷テスト（同時ユーザー1のデスクトップアプリのため）、ローカライズ（日本語のみ） |

### 1.3 品質目標（リリースの必須条件）

| No. | 目標 | 出典 |
|---|---|---|
| Q-01 | A-1〜A-6 の全受入基準を満たすこと | 機能仕様書 §4.7, §5.5 |
| Q-02 | `GLEM.Core` のテストカバレッジ 80%以上 | 機能仕様書 §7、基本設計書 §8 |
| Q-03 | S1/S2 不具合の残存ゼロ（§4.1 の重大度定義） | 本文書 §5.3 |
| Q-04 | T-12 の性能基準を満たすこと（開発環境での実測値を記録） | 機能仕様書 §7 |

## 5. CI 構成と品質ゲート

### 5.1 GitHub Actions ジョブ構成（例）

```yaml
name: GLEM-CI
on: [push, pull_request]
jobs:
  build-test:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - run: dotnet restore GLEM.sln
      - run: dotnet build GLEM.sln -c Release --no-restore
      - run: dotnet test GLEM.Tests -c Release --collect:"XPlat Code Coverage"
  coverage-gate:
    needs: build-test
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: カバレッジゲート（GLEM.Core >= 80%）
        run: |
          $cov = (Import-CoverageReport).GLEM_Core.Percent
          if ($cov -lt 80.0) { exit 1 }
```

### 5.2 ゲート判定

| ゲート | 条件 | 失敗時の挙動 |
|---|---|---|
| ビルド | `dotnet build` 成功 | PR マージ不可 |
| テスト | T-01〜T-11 の自動テスト全件パス（T-12 は M3 で定期実行） | PR マージ不可 |
| カバレッジ | GLEM.Core ≥80%（Q-02） | PR マージ不可 |

### 5.3 性能テストの運用（T-12）

- CI の常時ジョブではなく、M3 で基準機相当のランナー上を週次＋リリース前に実行する
- 判定は詳細設計書 §8.2 T-12 の方針に従い「閾値の2倍超過で失敗」（探索>120s、沈下>60s）
- 実測値（環境情報付き）を `docs/perf/` に時系列記録し、リグレッションを検証する

## 6. 不具合管理

### 6.1 重大度定義

| 重大度 | 定義 | 例 |
|---|---|---|
| S1（致命） | アプリ起動不能・クラッシュ・データ喪失の可能性があるもの | 保存ファイルが破損する、未捕捉例外で強制終了する |
| S2（重大） | 計算結果が A-1〜A-6 の許容範囲を外れる、主要機能が使えないもの | FS が参照値と ±0.01 を超過する、解析実行ボタンが無反応 |
| S3（普通） | 代替手段がある機能不全・表示不備 | CSV の列順違い、プロットの注記欠落 |
| S4（軽微） | 見た目の問題・文言の不統一 | 余白の崩れ、ラベル表記ゆれ |

### 6.2 ワークフローとスループット目標

```
新規 → 確認済 → 修正中 → 修正済 → 検証済 → クローズ
                ↑___________再開__________↓（検証で不適合の場合）
```

| 重大度 | 対応目標 |
|---|---|
| S1 | 発見当日に着手、2営業日以内に修正完了 |
| S2 | 3営業日以内に修正完了 |
| S3/S4 | マイルストーン終了までに解消（S3 は M3 まで、S4 は M4 まで） |

### 6.3 リリース判定（L4 エクジットと連動）

- S1/S2 の「検証済」未満の不具合がゼロであること（Q-03）
- Q-01〜Q-04 をレビュアーが書面で承認すること

## 8. リスクと対策

| ID | リスク | 影響 | 対策 |
|---|---|---|---|
| TRISK-01 | 検証ケースの参照値（既知解）が確定しない | L1 の T-01〜T-03 が完了判定できない | 基本設計書 RISK-02 と同一。M1 前半に独立タスク化し、出典候補（Das, Terzaghi 系文献）を事前にリストアップする |

| TRISK-03 | L3 システムテストの手動負荷（開発者兼任） | 見落としリスク | §3.3 チェックリストを PR テンプレートに組み込み、M2/M3 のゲートとして機能させる |
| TRISK-04 | GLEM固有の λc 近似式の意図しない変更（D-04） | S2 不具合の発生 | T-03の独立計算固定値、円弧時 λc=1.0、上限2.0を回帰し、完全なJanbu一般化法でない旨を明記する |
